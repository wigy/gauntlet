# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Web remake of Atari's 1985 coin-op **Gauntlet**: up to 4 players co-op online, one browser per player, through a lobby on a Node game server. TypeScript + Vite + Canvas 2D; the browser client has no runtime dependencies, the server uses `ws` (run with `tsx`).

## Commands

```bash
npm run dev                 # Vite dev server, with the game server attached on the same port (/ws)
npm run build               # typecheck + production build to dist/
npm start                   # production: serve dist/ + game server (PORT, default 8080)
npm run typecheck           # tsc --noEmit (this is the lint step; there is no ESLint)
npm test                    # vitest run
npx vitest run test/game.test.ts -t "opens doors"   # single file / single test
npm run import:g1           # download + convert all 125 arcade Gauntlet maps (see below)
npm run import:g1 -- 9 78   # convert only these level numbers and print them as ASCII
npm run import:g2           # download + convert the arcade Gauntlet II maps it can read (72 of 103)
npm run sprites             # re-slice art/sheets/* into public/sprites/*.png
bin/build-and-publish [VER] # docker build + push dataplug/gauntlet:VER (default: package.json version) and :latest
bin/update-prod             # ssh to the dataplug server, pull :latest and restart the `gauntlet` container
```

Server environment: `LEVELS=builtin|custom|arcade|arcade2` (default set for new games; arcade = `public/levels/gauntlet1`, arcade2 = `public/levels/gauntlet2`, falls back to built-in if not imported), `PORT`, `DATA_DIR` (default `~/.gauntlet/`: saved players in `players.json`, each player's levels in `levels/<player id>/`). **Deployment**: https://gauntlet.dataplug-oy.com runs as the `gauntlet` service in `~/dataplug/docker-compose-prod.yml` (behind the stack's nginx-proxy + Let's Encrypt), with the server's `~/.gauntlet` mounted at `/data` (`DATA_DIR`). The image never contains the arcade maps: `public/levels/gauntlet1`, `public/levels/gauntlet2` and `.import-cache` are symlinks into `/data`, so import them on the server with `docker exec gauntlet npx tsx tools/import-vgmaps.ts` (and `tools/import-g2.ts`) and restart the container. URL parameter `?level=N` makes games you create start at level N (for testing).

## Architecture

- **`src/core/` is pure simulation, no DOM.** `Game` (`game.ts`) advances one fixed `TICK` (1/60 s) per `step(inputs)`, where `inputs` is `Map<controllerId, PlayerInput>`. Rendering, audio and input only read game state and drain `game.events` (`say` / `sfx` / `flash`). Keep it that way: the determinism (all randomness goes through the seeded `Rng`) is what the tests rely on, and the server runs this same code.
- **Online play (server-authoritative)**: `server/lobby.ts` (transport-agnostic, unit-tested in `test/lobby.test.ts`) holds clients, rooms and saved players (`server/store.ts`). A room is `waiting` (anyone can join, any member can start), then `playing` (others can still jump in at the level start, up to 4), then `over` (back to the lobby after 5 s). It steps each running `Game` at 60 Hz with `{ online: true }` and sends every member a snapshot every 2 ticks, limited to entities near their hero (`AOI_X/AOI_Y`); full level tiles go out once per level, then only changed tiles (opened doors) and the item list when it changes. `server/attach.ts` adds the WebSocket on `/ws` to any HTTP server (the Vite plugin in `vite.config.ts` in dev, `server/main.ts` in production). Messages are typed in `src/net/protocol.ts`.
- **Client**: `src/main.ts` connects (`src/net/connection.ts`, auto-reconnect), shows the DOM screens in `src/ui/menu.ts` (name, lobby, waiting room, Esc pause menu), sends input only when it changes, and applies snapshots to `src/net/mirror.ts`, a `Game`-shaped copy whose entities keep their identity across snapshots so the renderer can interpolate and diff them. The player id lives in localStorage (`gauntlet.playerId`) and the server keeps the name for it. No client-side prediction yet, so movement has one round trip of input lag.
- **Level sets and the editor**: `server/levels.ts` (`LevelLibrary`) serves four sets: `builtin`, `arcade` and `arcade2` (Gauntlet II; each if imported) and `custom` = "My levels", which is per player: made in the editor, saved as `<DATA_DIR>/levels/<player id>/<id>.txt` plus `index.json` for play order, visible and editable only by that player id (owners are validated as UUIDs before touching the file system). Creating a game picks a set (lobby dropdown); a room snapshots the set's texts (custom: the creator's levels, shown as "<name>'s levels"), so others who join play the creator's levels and later edits don't affect running games. The editor (`src/editor/`, opened from the lobby) works on the level text format directly: paint with the legend characters (pen / rectangle / fill, undo, zoom and pan), check start/exit reachability with `bfsDistances`, save via `levelSave`, copy any built-in or arcade level (`LevelLibrary.get` populates wall-only arcade maps first and serializes with `levelToText`), and "Play test" creates a custom-set game that starts immediately at that level; leaving it returns to the editor. Ownership is only as strong as the player id in localStorage (no real accounts).
- **`online` mode in `Game`**: players come from `addPlayer()`/`removePlayer()` and `start()` instead of FIRE joins, there's no shared-screen limit, potions hit what's in the drinker's own view, and joins and revives happen at the level start. Without it (the default, used by `test/game.test.ts`), `handleJoins` binds a controller to a free slot on FIRE as in local co-op.
- **Controllers**: `InputManager` (`src/input/`) reports `kb1` (arrows, Z fire, X potion) and `pad0`..`pad3`; online, `combined()` merges them into one player's input. It ignores keys while a menu or text field is in use (`enabled`).
- **Coordinates are in tiles.** An entity's `x`/`y` is its centre, and collision uses axis-aligned boxes (`ENTITY_RADIUS`). Levels can wrap on x and/or y (torus mazes), so **always** use `game.dxw()`/`dyw()` for deltas between positions and `wrapX`/`wrapY` after moving. Never subtract coordinates directly. `tileAt()` handles wrapping and treats out-of-bounds as wall.
- Monsters are found through a tile-keyed spatial hash (`buckets`). Call `rebucket()` after moving one and `unbucket()` when killing one. Generators live in `generatorAt` (static, keyed by tile index).
- **Camera**: online, the mirror's camera follows your own hero. In local mode, the renderer sets `game.viewW/viewH` (in tiles) on resize, the camera is the wrapped centroid of the living heroes, and `movePlayerAxis` stops heroes walking out of each other's view, as in the arcade.
- **Turning**: heroes and monsters face one of eight directions (`fx`/`fy`). Moving in a new direction first turns them, and they don't walk until `turn` (`TURN_TIME`) runs out, so a tap turns in place, as in the arcade. Monsters pick their direction with a little hysteresis so they don't keep stopping to turn.
- Tuning numbers (hero stats, monster stats, health and food values, limits) are all in `src/core/defs.ts`.
- **Gauntlet II mechanics** live in the same `Game`. Tiles (`Tile` in `level.ts`; at most ten, since the protocol sends one digit per tile): traps remove every trap wall, breakable walls take `BREAKABLE_HITS` shots (`wallHits`), stun tiles stun (`Player.stun`), transporters send you to the nearest other one (`portedTo` stops the bounce back), force fields burn while `forceFieldOn(time)` (all in step; the snapshot carries `time` for the client). Use `isSolid()`/`isWallLike()` rather than comparing with `Tile.Wall`. Monsters: dragon (big: `radius`, kept in `bigMonsters` since the buckets don't cover it), super sorcerer, acid puddle and thief (`loot`, `life`, spawned by `stepThief` on `thief: yes` levels); `tough` monsters ignore melee and a potion only stuns them (`Monster.stunned`). Items: amulets (one at a time, `Player.amulet`/`amuletTime`; super shots count shots), poison (`dizzy` reverses the controls), the It ball (`Player.it`: every monster targets that hero, touching passes it on). On any level, staying `WALLS_TO_EXITS_TIME` turns all walls into exits, as in the arcade. Tests are in `test/gauntlet2.test.ts`.

## Levels

- Text format documented at the top of `src/core/level.ts`: `key: value` header (`name`, `wrap`, `rank`, `style: g2`, `thief: yes`), `---`, then a character grid (`#` wall, `D` door, `E` exit, `S` start, Gauntlet II tiles `^` trap `%` trap wall `*` breakable `~` stun `@` transporter `=` force field, items `FCPKTABI`, generators lowercase `grodlxu`, monsters uppercase `GRMLOXUZHY`).
- `src/levels/builtin.ts`: original hand-made levels, always available. Custom levels from the editor live outside the repo (see Level sets above). `test/level.test.ts` checks every built-in level is rectangular and its exit is reachable.
- Level sets are served from `public/levels/<set>/index.json` (an ordered array of file names) plus the `.txt` files, and loaded by `main.ts`.
- **Arcade maps**: `tools/import-vgmaps.ts` downloads the arcade Gauntlet I rips from VGMaps and classifies 16 px cells into wall/floor/exit by colour clustering. The rips are 33x33 cells; the 33rd row/column duplicates the first, which the importer uses to detect wrapping. The rips contain **only walls and exits**, so `populate()` places the start, generators, monsters and items deterministically from the seed and level number. Output (`public/levels/gauntlet1/`) and the download cache (`.import-cache/`) are gitignored on purpose: the layouts are Atari's, so don't commit them.
- **Gauntlet II maps**: `tools/import-g2.ts` reads the VGMaps sheets (`GauntletII-*Levels-*.png`: nine 512x512 maps each, the first sheet starting with the demo maze). Each map has its own crop offset and palette, so the importer searches the grid offset, finds floor/wall palettes, red sprite blobs (transporters ~150 px, other sizes are force field posts) and rare-colour patches (bright = breakable wall, dim = stun tile); the comment at the top explains it. It's heuristic: maps whose walls it can't read (perspective walls, low contrast) are skipped and listed. Trap walls look like plain walls in the rips, so traps aren't imported. The legend on the last sheet (wall/floor types, monster table) is the reference for what things look like. Output (`public/levels/gauntlet2/`, `style: g2` so `populate()` adds Gauntlet II monsters and items) is gitignored like the Gauntlet I import. `tools/vgmaps.ts` is the shared download cache.

## Graphics

- `art/sheets/` holds the AI-generated source sheets (made with the Gemini image tool: sprites on a flat magenta background, plus a 2x2 tile grid). The tool saves JPEG data even when asked for `.png`, so the slicer sniffs the format.
- `tools/slice-sprites.ts` finds each sprite as a blob of non-magenta pixels, names them in reading order from its `SHEETS`/`TILES` tables, and writes 128x128 soft-edged transparent PNGs to `public/sprites/` (committed), clipping each crop to the sprite's own blob and removing magenta fringe. If you regenerate a sheet, keep the same sprite count and order, or update those tables.
- `src/render/sprites.ts` loads them asynchronously. The renderer draws a sprite if it has loaded and otherwise falls back to its canvas-shape drawing, so a missing sprite never breaks the game. Wall colour per level is a cached hue-rotated copy of one of the two wall textures (`WALL_VARIANTS`). Heroes and monsters (except the acid puddle) have walk sheets in `art/sheets/walk/<name>.jpg`: a 5x3 grid, columns facing s/se/e/ne/n and rows the frames stride/stand/stride, cut by `gridSprites` into `<name>-<dir>-<frame>.png` with one shared scale per sheet so frames don't jitter. The diagonal columns come from separate `<name>-diag.jpg` sheets (2x3: se, ne), because the generator draws diagonals poorly in the 5-column sheet; they're scaled to the main sheet's figure height. West-facing directions are horizontal mirrors (`walkDir`). The renderer plays frames 0,1,2,1 while an entity moves, at a rate scaled by its speed, and falls back to the single `<name>.png` until they load.
- Rendering is smooth-scaled (no pixelated mode). `main.ts` calls `renderer.snapshot(game)` before each tick and passes the tick fraction to `draw()`, which interpolates heroes, monsters, shots and the camera. Cosmetic effects (particles, hit flashes, score pop-ups, death bursts) come from diffing game state between frames in `Renderer.trackChanges`, so `src/core` stays free of render events. A low-res light map (`drawLighting`) is multiplied over the scene; `src/render/fx.ts` holds the particles and cached glow/shadow textures. Fonts (Cinzel, Inter) come from Google Fonts with system fallbacks.
- **First-person TV** (`src/render/firstperson.ts`, toggled with V and remembered in localStorage `gauntlet.tv`): a small Wolfenstein-style raycaster drawn into a buffer of at most 200 px wide, shown in the side panel below the player cards (which shrink to make room; the TV scales down or hides on short windows) inside the `tv.png` set (the screen rectangle is found at runtime as the transparent hole in it). It shows our own hero's view online, or the first living hero locally. Textured walls/doors (the level's wall variant), floor (tinted for exits and Gauntlet II tiles) and `ceiling.png`; everything else is billboards with a z-buffer, and walkers use the walk frame for the side the camera sees. The camera angle swings toward the hero's facing; a dead hero shows static.

## Not implemented yet

Client-side prediction, accounts/auth (a player id is just a bearer token in localStorage), friendly-fire stun, attack and death animations. From Gauntlet II: moveable blocks (imported as breakable walls), "It" as a monster (here it's a ball you pick up), exits to other levels ("EXIT TO 6"), fake and moving exits, treasure and secret rooms, invisible-wall and other per-level modifiers, the mugger, permanent power potions, choosing hero colours.
